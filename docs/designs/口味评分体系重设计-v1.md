# 口味评分体系重设计 v1（owner 主导 · 两段式 · 分层执行 · 去偏）

> 基于代码实况：v1 贝叶斯引擎（`dev/engine/bayes.py`，Beta 共轭、可复算）、v2 众包契约
> （`CROWD_CONTRACT.md` kind=note/rating、R6 评分门、`crowd_reviews.trust_level`、
> `UNIT_PRICE={note:0.5, rating:1.0}`、`food-atlas-app` 前端"不做评分"立场）。
> 设计日期：2026-10-06。所有数值为 v1 默认参数，入 `model_version` 管理，可调参重算。

## 0. 五条设计公理（对应需求 1–5）

- **A1 owner 即标尺**：1–5 分的绝对刻度由 owner 的口味判断定义；机器与众包只产生"需要校准到 owner 标尺的证据"。
- **A2 两段式**：口味 = 准入（能不能进比较集）+ 排名（进了集怎么排）。任何"平均分"都不直接对外发布。
- **A3 分层执行**：采集（S1）→ 入库整理（S2）→ 统筹打分（S3）共享一套指标定义，但物理上分三步跑，S_n 的输出是 S_n+1 的唯一输入；S3 是纯函数（同输入同输出，可复算）。
- **A4 分布≠口味**：笔记量、价格带、知名度造成的覆盖差异，只影响"置信度与准入阈值"，绝不进入口味后验的方向性更新。
- **A5 人机分工**：人类（owner）主导口味结论；数据/机器负责准入把关、质量门、校准计算、去偏数学与漂移告警。机器可以自动收紧，永不能自动放松任何门槛。

## 1. 概念模型与对象

- 评分对象 = **(店铺 s, 菜系上下文 c)**。一家店可在多个菜系 cell 下各有独立的口味状态（如"本帮菜"和" brunch"分开评）。
- 三个状态机：**收录项**（note/rating 条目，S1→S2）、**准入状态**（candidate / admitted / rejected / owner_admitted，S2→S3 定）、**口味状态**（后验参数 + 分层排名，S3 产出）。

## 2. 模块划分

| 模块 | 职责 | 现状 |
|---|---|---|
| M0 owner 采集端 | owner 到店评价（1-5+理由）、成对比较（"A 的 X 比 B 好"）、准入裁决、发布批准 | **缺失，需新建**（最低可用形态：结构化表单/飞书多维表，不必先做 App） |
| M1 插件采集端 | 参与者采 note / rating（评分走插件内交互 UI） | note 已通；rating 交互 UI 缺失（本方案 §8 落地项） |
| M2 采集门（S1） | R6 等字段/质量校验，只验"能不能收"，不打分 | 服务端已就绪 |
| M3 入库整理（S2） | 实体锚定（entity_match）、去重、来源分级、provenance 落章、聚类标记（同作者/同话题/同时段）、计算数据侧准入候选 | 部分就绪（ingest 需拆出整理层） |
| M4 统筹打分（S3） | owner 先验、证据池化（加权伪计数）、标尺校准、去偏、BT 排名、CI 计算、版本化输出 | v1 `bayes.py` 模式可复用（确定性重算 + signals_used 留档） |
| M5 输出与告警 | 分层排名 + CI 展示口径、漂移告警、发布批准流 | 前端立场：只在 owner 批准后按菜系批次发布 |

## 3. 指标与权重（显式默认参数）

### 3.1 证据分级与伪计数倍数 m（对 Beta(α,β) 的等效观测数）

| 证据类型 | 来源 | m（默认） | 进入口味后验？ | 说明 |
|---|---|---|---|---|
| owner 到店评分 | M0 | **25** | ✅ 主输入 | r∈[1,5] 转 Bernoulli：p=(r-1)/4，α+=m·p，β+=m·(1-p) |
| owner 成对比较 | M0 | **≈40 等效**（BT 全权重） | ✅ 主输入 | 见 §4.2；owner 一次"A≻B"≈40 条众包 rating 的信息量 |
| owner 一句话印象 | M0 | 8 | ✅ 仅情感方向 | 无分值，只有正/负/中，按方向给 (α 或 β) += 8·0.6 |
| 众包 rating（校准后） | M1 | **1.0** | ✅ 弱输入 | 先经标尺映射 M 校准（§5），再入池 |
| 众包 note 情感信号 | M1 | 0.3 × signal_strength | ✅ 弱输入 | 沿用 v1 四标签 + 强度；营销嫌疑不计分只计数 |
| 平台聚合分（高德/点评） | 外部 | 0.5 | ❌ 不进口味后验 | 仅用于准入交叉印证与校准参照（立场：平台分≠口味） |

**owner : 机器信号比例**：口径上 owner 单次到店 = 25 条校准后众包 rating = 约 80 条原始情感信号；owner 单次成对比较 = 40 条众包 rating。批量口径：任一 (s,c) 后验中 owner 证据占比低于 1/3 时，该 cell 输出标记 **owner 锚不足**，只出排名序、不出绝对分。

### 3.2 上限与折扣（防量不换质）

- 单 (s,c) 有效证据上限 **cap=20**（按来源去重后）：第 20 条之后的同质证据边际贡献递减（×0.5^k）。
- 同源聚类折扣：同一作者/同一话题簇/7 日内同时段笔记，第 n 条乘 ρ^n（ρ=0.5）。
- 营销嫌疑信号：不计 α/β；单店占比 ≥30% 打 marketing_flag 并冻结该店自动准入（人工复核）。

## 4. 两段式口味机制

### 4.1 第一段：口味准入（admission）

**数据侧门槛（S2 产出候选，S3 确认）——全部按 strata 分档（§6.1）：**

| 门 | 规则（默认） | 否决权 |
|---|---|---|
| G1 独立来源数 | 知名带 ≥10 / 普通带 ≥5 / 小众带 ≥3（作者去重后） | 机器可收紧 |
| G2 交叉印证 | ≥2 个独立来源类型（众包/平台/owner 至少两类） | 机器可收紧 |
| G3 时效 | 最近 18 个月内有信号 | 机器可收紧 |
| G4 红旗 | 无未处理 marketing_flag / 批量异常 | 机器可收紧 |

**owner 侧（一票权）**：`owner_admitted`（直接放行，可附理由，记录审计）；`owner_veto`（一票否决数据候选，必须填理由）。最终状态：
`admitted = (数据候选 ∧ 未否决) ∨ owner_admitted`；`rejected = 数据否决 ∨ owner_veto`。
**未准入 ≠ 难吃**：未准入在一切展示中呈现为"样本不足/未验证"，与低分视觉上严格区分（A4）。

### 4.2 第二段：准入集内比较排名

- 排名在 **菜系 c 内部** 进行（跨菜系不比较）。
- **主模型：Bradley-Terry**。每家店潜变量 γ_s（初值 1）：
  - owner 比较"A≻B"：`log γ_A += η·(1 − P(A≻B))`，`log γ_B += η·(0 − P(A≻B))`，P = γ_A/(γ_A+γ_B)，η=1.0（全权重）
  - 从众包文本抽取的共现比较（如"A 比 B 地道"，带抽取置信度 conf）：η=0.05·conf
  - owner 分值 r 也折算为对比较弱证据：与 owner 已锚店 o 比较，等效胜率 p=(r−1)/4，η=0.5
- **校正项（ shrinkage ）**：γ 估计向"先验秩"收缩：λ = m_owner/(m_owner + m_crowd)；估计秩 = λ·秩(BT on owner证据) + (1−λ)·秩(BT on 全部证据)。λ→1 时众包几乎不能移动排名；λ<1/3 时输出"锚不足"。
- 输出：`rank_in_cuisine`、`γ`、`CI`（BT 后验自助法或 Laplace 近似）、`anchor_state`（anchored / rank_only）。

## 5. 贝叶斯迭代与校准机制

### 5.1 更新流（每次 S3 批次）

```
输入: evidence_items(S2) + owner_reviews/comparisons(M0) + 上一版 taste_state
1) 校准: 重拟合 众包分→owner 标尺 映射 M_c（isotonic 回归，按菜系分组；
   数据不足的菜系退回全局线性映射，斜率先验=1 收缩）
2) 漂移检查: |M_c_new − M_c_old| > 0.3 分 → 告警 owner，不自动切换
3) 证据池化: 按 §3.1 权重与 §3.2 折扣更新各 (s,c) 的 Beta(α,β)
4) 排名: §4.2 BT + shrinkage
5) 准入: §4.1 规则求值 + owner 一票记录
6) 输出: taste_state 全量重写（delete+insert，model_version 递增，
   每个输出行携带 inputs_manifest，复算可逐位验证——沿用 v1 bayes.py 模式）
```

### 5.2 owner 新判断的注入方式（迭代更新机制）

- **即时**：owner 每次到店/比较提交 → 进入 S2 → 下个 S3 批次生效；批次可按需手动触发。
- **强移动 + 冲突记录**：owner 证据 m 大，后验快速向 owner 移动；若 owner 新判断与现后验冲突（|r − 后验均值| > 1.5 且 CI 窄），不静默覆盖——记 `owner_conflict` 并推给 owner 复核（可能是 owner 换口味了、店换了厨师、或数据有鬼，三种都值得 owner 知道）。
- **先验演化**：owner 各菜系长期均值构成下一版 Beta 先验的超参数（empirical Bayes），实现"越评越准"而不漂移失锚。

## 6. 偏差校正策略

### 6.1 分层（stratification）

- 维度：菜系 c × 价格带（贵/中/平，三档）× 知名度（知名/普通/小众，三档）。
- 每 cell 独立计算：准入阈值（G1 分档）、cap、CI 基准。**跨 cell 不直接比绝对分**，跨价格带比较只通过 owner 锚 visit（owner 在各 cell 的到访分是唯一跨 cell 桥梁）。
- **owner 锚配额采样**：owner 每季度在每个活跃 cell 至少 1 次到访（结构化提醒）；缺锚 cell 输出 rank_only。

### 6.2 覆盖偏差处理

- 笔记多 ≠ 口味好：volume 只影响准入与 CI 宽度，后验更新受 cap=20 封顶（§3.2），5000 条笔记的店不会比 20 条独立证据的店"更确定地好吃"。
- 小众店保护：小众带 G1 阈值降至 3，且 owner 一次到访（m=25）即可越过数据门槛（owner_admitted 路径）。
- 名气聚团（herding）：同时段激增笔记按时间簇折扣；同选题簇（探店打卡模板文）降权。
- 价格带选择偏差：中档店笔记少 → 中档 cell 的 CI 普遍偏宽 → 展示"待验证"而非让缺数据在排名上自动沉底；S3 输出必须附带各 cell 覆盖率报告给 owner。

### 6.3 置信度输出规范

每个对外分数必须带：CI 宽度、有效独立证据数 n_eff、owner 锚状态、model_version。CI 半宽 >0.8 分或 n_eff<cap 下限 → 只出"候选排名（低置信）"，不进任何公开榜单。

## 7. 人机分工规则（RACI）

| 决策 | owner | 机器/数据 | 众包 |
|---|---|---|---|
| 定义 1–5 标尺与菜系taxonomy | **R** | C | — |
| 口味准入最终态 | **R**（一票） | R（数据候选） | — |
| 数据质量门（R6 等） | A | **R** | — |
| 证据加权/校准/去偏/排名计算 | A | **R** | — |
| 口径与阈值收紧 | A | **R**（可自动） | — |
| 口径放松 / 反否决 | **R**（唯一入口） | — | — |
| 提交 note/rating 证据 | I | C（校验） | **R** |
| 发布（按菜系批次） | **R**（批准） | C | — |

硬规则：①机器任何"放松"动作禁止落库；②众包参与者永远看不到分数与排名（防 gaming 与锚定污染）；③owner 每次覆盖必须留理由，覆盖记录本身作为高权重证据进入审计。

## 8. 分阶段执行流程（S1→S2→S3 数据契约）

| 阶段 | 输入 | 处理 | 输出表 |
|---|---|---|---|
| **S1 采集** | 人（owner 表单/插件交互）在店/读笔记 | 字段与质量门校验（现有 R6 扩展 rating 交互），**不打分** | `crowd_proofs`(kind=note/rating)、`owner_reviews`、`owner_comparisons`（raw 状态） |
| **S2 入库整理** | S1 输出 | 实体锚定、作者/话题/时间聚类、来源分级、provenance、计算 G1–G4 候选 | `evidence_items`（每行=一条规范化证据：source_tier, cluster_id, p_strength, provenance） |
| **S3 统筹打分** | S2 输出 + owner 裁决 + 上版 taste_state | §5 流程全量重算（确定性、model_version 递增） | `taste_admission`、`taste_state`、`calibration_runs`、`alerts` |

铁律：S1 不得调用 M4 任何函数；S2 不得更新 α/β；S3 不直接读 raw 表（只读 S2 产物 + owner 裁决表）。

## 9. 与现有代码的映射与改造清单

1. **M0 新建**：最低可用 = 飞书多维表/结构化表单（店、菜系、1–5、理由、成对比较 A≻B、准入裁决），同步脚本写入 `owner_reviews`/`owner_comparisons`。
2. **M1 插件**：详情页加评分交互（1–5 + ≥8 字理由 + 可选"比另一家更好"），产出 `kind:"rating"` 且锚定已收录 note_id（天然满足服务端 R6）；`target` 字段终于生效。
3. **服务端**：新增 5 表（§8）；`crowd_ingest.py` 拆分为 S2 整理器（不再直接算进度以外的隐式打分）；`_write_review` 保留为 S2 的子步骤。
4. **M4**：以 `dev/engine/bayes.py` 为骨架新写 `engine/taste_state.py`（Beta 池化 + BT 排名 + isotonic 校准 + 全量确定性重算 + inputs_manifest 留档）。
5. **crowd_crossed**：本期不实现多自动升级，改为"owner 标记交叉证实"手动升 trust（避免无主的自动化）。
6. **前端**：延续不做公开评分立场；owner 私有面板展示分层排名 + CI + 告警（发布批准流）。

## 10. 里程碑

- **P0（1–2 天）**：建表 + `taste_state.py` 骨架 + 用现有 77 条 note 回放跑通 S2→S3 空转（无 owner 数据 → 全部 rank_only/candidate，验证管道）。
- **P1（1 周）**：M0 表单上线，owner 先评 20 家店 + 30 组成对比较 → 首批 anchored 菜系 cell 出分。
- **P2（2 周）**：插件 rating 交互 UI + `target` 生效 + 众包校准回路闭合。
- **P3（持续）**：分层覆盖率报告、漂移告警、季度 owner 锚配额采样、按菜系批次发布。

## 11. 开放问题（需 owner 拍板）

1. 菜系 taxonomy 的粒度（大类 10+ 还是细分 30+？影响 cell 数与锚配额负担）。
2. 成对比较的录入摩擦 vs 精度收益：建议起步用"同菜系三选一"轻交互替代自由 A/B。
3. 是否引入 LLM 从笔记正文抽取情感/比较信号（会触碰 food-atlas 既有"不编造"立场，需显式授权与抽检）。
4. 价格带三档的划分数据源（高德人均 vs 手工标注）。
