1开发方法论：一套通用建造方式
8 个模块共享同一种"建造方式"，保证高效开发 + 持续可演进。核心：最小内核 → 插件适配 → 契约演进 → 复用证明。
原则 A · 最小内核 + 插件
每个模块拆成core（确定性内核，通用） + adapters（插件，领域/平台差异）。内核一旦稳定几乎不改；新需求 = 加插件，不动内核。采集器加平台=加连接器，清洗器加规则=加校验器，评分器加维度=加 rubric。
原则 B · 契约先行 + semver
模块对外的输入输出以 JSON Schema 契约定义，版本走 semver。新增字段走可选扩展，禁止破坏性变更。契约是模块之间唯一的握手方式，契约稳定 = 模块可独立演进。
原则 C · 配置驱动
一切领域知识（词根/权重/阈值/抽样框）来自 Manifest 与本体包。升级需求 = 改配置 + 加插件，永远不需要重写内核。代码里 grep 不到业务词。
原则 D · 确定性 + 可复跑
机械环节（清洗/去重/校验/门控/写库）全部确定性代码，幂等、可重跑、有回读断言。模型只做发现与语义判断。这保证"升级后重跑"成本极低。
原则 E · 测试金字塔
契约测试（schema 校验）> 单元测试（内核逻辑）> 回归集（点名店 100% 命中）。每次改动跑全套，全绿才算完成。回归集是"不断升级但不出错"的保险丝。
原则 F · 复用证明
每个模块必须至少被两个项目消费（eat our own dog food）。单一消费者说明抽象过度或还没通用化——写进验收，不做口头承诺。
通用演进路径（每个模块都走这条）：
v1 立内核（把现有脚本能力抽成最小可用的 core，先跑通上海项目）→
v2 插件化（差异全部插件化，换城市/换领域只换配置与插件）→
v3 平台化（提供 CLI/SDK/DAG 三入口，接第二个项目证明复用）。每一级都必须 audit 全绿才进下一级。
2M1 采集器 Crawler
目标：一个「按 Manifest 采任何领域数据」的通用采集引擎。开发重点是连接器插件体系 + 反爬服务 + 召回引擎，三者彼此独立。
M1
采集器 Crawler
数据获取 · 领域无关采集引擎
独立工具 · 插件体系
开发方式（高效且可演进）
STEP 1 · v1 立内核
采集调度内核
把现有 discovery_engine / 抽样框 F1–F6 抽成 core：网格解析、配额管理、去重调度、结果落 raw/。先复用现有 xhs / michelin / tencent_sig 脚本跑通上海。
STEP 2 · v2 插件化
连接器 + 反爬服务
每个平台一个 connector 插件（entry_points 注册）；反爬独立成服务（代理池/账号池/限速/风控语义）。新平台 = 新插件，内核零改动。
STEP 3 · v3 平台化
召回引擎 + 复用证明
权威全量召回（sitemap 对账）、集团/主厨树、LLM 舰队等作为可选引擎插件。接 Livehouse / 房源项目证明采集与领域无关。

3M2 清洗器 Cleaner
目标：raw → 标准实体（canonical entity）。开发重点是schema 硬校验 + 实体解析 + 事实核验，全部确定性、可复跑。
M2
清洗器 Cleaner
数据中台 · 清洗与标准化
中台模块 · 确定性内核
开发方式（高效且可演进）
STEP 1 · v1 立内核
校验 + 实体解析
把 stage1_validate / entity_align / merge_duplicates 抽成 core：schema 硬门、名称归一、同址合并。Pydantic 定义契约即校验器。
STEP 2 · v2 插件化
校验器 + 地理编码 + 事实核验
领域校验规则（如菜品名≠餐厅名）做成 validator 插件；地理编码（地址→GCJ02）独立服务；事实核验走搜索引擎+权威通报（不等 UGC）。
STEP 3 · v3 平台化
字段保鲜 + 血缘
字段级 last_verified / stale（30/90/180 天）、变更留 history。任一"实体型"领域（房源/POI/商品）换 schema 即用。

4M3 评分器 Scorer
目标：标准实体 → 多维评分 + 污染检测 + 准入决策。开发重点是rubric 配置化评分引擎 + 软广多信号模型 + 贝叶斯置信。
M3
评分器 Scorer
数据中台 · 评分与准入
中台模块 · 维度可配置
开发方式（高效且可演进）
STEP 1 · v1 立内核
rubric 评分引擎
把现有四项评分（客观/食客/口味/背书）重写为「维度 × 权重 × 归一化」的配置驱动引擎；准入闸门（≥2 独立声音 + 阈值）独立成判定器。
STEP 2 · v2 插件化
污染检测 + 置信
软广/硬广/工业化三类独立建模为 detector 插件；评论级 p_softad 用 scikit-learn 经典 ML（可解释特征）；贝叶斯置信与时间衰减作为 score 后处理。
STEP 3 · v3 平台化
跨领域 rubric + 复用证明
housing 本体包自带 rubric（笋盘度/租售比），同引擎零改动跑通；污染检测迁移到"假房源/虚假在售"场景验证复用。

5M4 本体库 Ontology
目标：领域知识打包成可安装、可版本化、可回滚的本体包。这是"换领域不换工具"的钥匙，也是整个平台最容易做好的部分——因为本质是结构化配置 + 校验 + 版本管理。
M4
本体库 Ontology
领域知识插件 · 换领域的钥匙
配置包 · 唯一领域入口
开发方式（高效且可演进）
STEP 1 · v1 立内核
包结构 + 校验器
定义本体包目录规范（taxonomy / keywords / scoring_rules / regression_set / source_plan / schema）；Pydantic 校验器保证包合法才可安装。现有 templates/ 7 模板直接演化。
STEP 2 · v2 版本化
semver + 安装/回滚
本体包版本号 semver；toolbox ontology install / verify / rollback；包注册表（ledger）记录每个项目引用哪个版本。
STEP 3 · v3 生态化
包市场 + 跨领域
housing / livehouse 本体包随项目沉淀；冷启动流程 = 半自动填包（LLM 起草 + 人工审）。包与包之间可继承（food-cn-v2 继承 food-cn-v1）。

6M5 编排器 Orchestrator
目标：把 crawl → clean → score → audit → deliver 编排成可定时、可续跑、可告警的 DAG。开发重点是轻量起步（cron + CLI）→ 渐进到 DAG 引擎，避免一上来就背 Airflow 的运维成本。
M5
编排器 Orchestrator
编排调度 · 工作流引擎
平台服务
开发方式（高效且可演进）
STEP 1 · v1 立内核
pipeline.yaml + CLI 串行
每项目一份 pipeline.yaml（阶段顺序/参数/重试）；toolbox orch run 按序串行执行各工具 CLI。先满足"能自动跑"，不引入重型引擎。
STEP 2 · v2 调度化
cron 定时 + 看门狗
cron/rrule 定时触发；看门狗 20min 巡检、断线自愈、告警路由（飞书/TG）。云端常驻（v2.1 云上运行约束）。
STEP 3 · v3 DAG 化
Prefect 编排
多阶段并行、断点续跑、失败重试开箱即用。仅当并行任务与续跑需求明确后引入，避免提前背上运维成本。

7M6 审计器 Auditor
目标：只读体检 + 覆盖审计 + 发布闸门。开发重点是把现有 release_audit A–H 八类扫描沉淀为可配置的 gate 套件，全绿才放行发布。
M6
审计器 Auditor
质量与发布门 · 只读体检
发布闸门 · 全绿才上线
开发方式（高效且可演进）
STEP 1 · v1 立内核
gate 套件骨架
把 release_audit / regression_check / duplicate_audit / stage6_coverage / fact_evidence_gap 抽成统一 gate 框架：每类扫描 = 一个 gate 插件，输出结构化报告 + pass/fail。

10.2 关键借鉴结论（值得立即抄的 3 个）
① crawl4ai 的 sitemap 挖掘
解决权威全量召回的最高性价比方案：解析 robots.txt + 全量 sitemap + Common Crawl 历史 URL——直接替代手工对账米其林/黑珍珠索引。
② 贝叶斯平均评分（有现成 skill）
LobeHub 的 algo-rank-bayesian 就是一个可直接借鉴的评分 Skill：BR=(Cm+navg)/(C+n)，解决小样本评分虚高——正好是我们的"食客证据不足"痛点。
③ datacontract-cli 契约治理
数据契约 lint / 测试 / 破坏性变更检测一键化——把"契约先行 + semver"从口头变成 CI 里的硬检查。
